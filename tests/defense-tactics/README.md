# Fire Siege tactics acceptance

Run from the project root with Godot 4.6.1:

```sh
godot --headless --path . --fixed-fps 60 -- --defense-tactics-test
godot --path . -- --defense-tactics-visual
godot --path . -- --defense-tactics-benchmark
```

The test script is `scripts/defense_tactics_tests.gd`. It uses the real game, director, card picker, hero, enemy collision/health, tower projectiles and imported Blender fire animation. Numbered keyboard input and real mouse motion/press/release events at each button both select cards. Pointer events enter the viewport in local coordinates so the test respects the game's 1440×900 canvas independently of its window size. Test fixtures skip roster time only when isolating a particular effect; they still use the production card validation and application paths.

Coverage includes:

- Compact 160×760 Fire Siege bounds, matching physical floor, a straight center route from entrance to shrine, and all 24 tower mounts/purchase positions contained in six road stations.
- Exactly three unique eligible choices before every wave; first-choice ice/fire/gold; pause and Esc/Resume protection; invalid, absent, duplicate and conflicting choices rejected; dependencies and stack limits.
- Ten actual finite 600-enemy rosters, center-lane arrivals, eight-spawn update budget, live cap, runners/brutes/shields, one boss inside wave 5 and wave 10, exactly ten recorded choices, no wave or choice after victory.
- Normal and hard resources, four initial hard-mode towers, gold-funded construction, retry preserving difficulty while clearing run upgrades, repair/fortification and real bounty payouts.
- Real blue crystal projectile impacts, finite nonstacking slow, measured lane movement with/without chill, boss slow resistance, Shatter timing, damage/reload/range upgrades, tower-level upgrades retaining cards, both mutually exclusive tower branches.
- Actual wide-cone damage, armor-piercing blasts, finite pooled ground-fire damage, pause and wave cleanup, shield front/rear/heavy interactions, boss warning/impact/recovery, double-damage weak point, cover/jump/dodge protection and death cleanup.
- Existing movement, double jump, evade, pipe combo, Sky Strike, coins, chain sweep, spin, surge, gold flight and Edo character/ranged combat.

`campaign.json` records all role totals, boss tiers/profiles and the ten chosen cards. The functional suite resolves the 6,000-actor roster with real enemy damage/death calls to test accounting; natural-play balance is measured separately. Visual mode additionally saves opening draft, hard construction, ice, active ground fire, boss warning/weak point and victory screenshots.

The legacy `--defense-fire-*` / `--tower-defense-beta-*` flags disable tactical drafts so the earlier 93-check mixed-tower regression stays available. The original `--tower-defense-test` remains the 59-check three-lane defense regression.

## Rendered performance

The benchmark runs two approximately four-second samples after shader/targeting warmup. Both retain 180 durable wave-10 actors with real AI, including roles and a boss, and all 24 towers at level 3. The overview distributes targets across all six stations so all twelve fire towers and twelve cannons work. The second view concentrates the 180-actor swarm at the front parapet, exposing nearby role/status geometry and close combat. All hero/enemy fixtures remain inside the compact battlefield; overview cameras may sit beyond its edges.

This is a synthetic maximum-card stress test: it enables more numeric card stacks than a legal ten-pick run can collect, plus ice, Deep Winter, Shatter, siege shells and ground fire. Actual projectile collisions, armor, slow expiry, cone/raycast damage, pools and Blender animation remain enabled. No renderer timing is taken in headless mode.

`performance.json` reports average/p95/maximum frame time, process and physics CPU, render CPU, draw calls, node/projectile/flame/pool peaks, chilled enemies, real damage pulses and towers firing. GPU timing is marked unavailable when the backend reports zero. Results and screenshots are generated by the rendered run; do not interpret an empty or headless field as performance evidence.
